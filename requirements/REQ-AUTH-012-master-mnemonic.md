# Master-secret derivation from a BIP39 mnemonic — Manager-compatible helpers

The SDK SHALL provide two public helpers that reproduce Encedo Manager's
master-persona derivation bit for bit:

1. `ehem_mnemonic_generate(char **words_out)` — 256 bits from the
   crypto backend's RNG → a 24-word BIP39 English mnemonic (8-bit
   checksum, words joined by single spaces), library-allocated, freed
   with the matching free function (REQ-API-005).
2. `ehem_master_secret_from_mnemonic(const char *words, uint8_t
   secret[32])` — validates the mnemonic (24 words from the English
   list, checksum correct; otherwise `EHEM_ERR_ARG` with detail, no
   derivation) and derives the 32-byte master secret the Manager
   derives, which `ehem_device_init` (REQ-AUTH-011) turns into
   `cfg.masterkey`.

**Derivation, pinned to the Manager (`build.js:692-697`, `jsbip39_v1.js`):**
- `seed` = PBKDF2-HMAC-SHA512(password = NFKD(mnemonic), salt =
  `"mnemonic"` (empty BIP39 passphrase), 2048 rounds, 64 bytes);
- `seedhex` = lowercase hex of `seed` (128 characters);
- **secret = the 32 bytes encoded by `seedhex[1..65)`** — the Manager's
  `substr(1, 64)` takes 64 hex characters from offset **1**, i.e. the
  seed shifted left by one nibble (`secret[i] = (seed[i] << 4) |
  (seed[i+1] >> 4)` for i = 0..31). This is almost certainly an
  off-by-one in the Manager, and it is the behaviour that must be
  matched: a device initialised by the Manager holds the key derived
  this way, and the Manager's master-passphrase prompt derives it the
  same way at login;
- the X25519 keypair from `secret` follows REQ-AUTH-001's shim
  (`ehem_x25519_keypair_from_seed`; nacl's `fromSecretKey` clamps the
  scalar inside scalarmult — same public key).

The mnemonic is input data, never retained; `secret` and the seed are
zeroized after use. The English wordlist is vendored into the library
(2048 words; license to be confirmed from `jsbip39_v1.js`'s header —
iancoleman/jsbip39 is MIT — before vendoring, REQ-BUILD-003 style).

**Rationale:** the firmware's master role is admin-only (every keymgmt
and crypto handler rejects `sub="M"`; config writes accept U or M), so
the master persona is the "lost user password" recovery path: rotate
`userkey`, wipe. The Manager's settings-page prompts take the 24 words
for exactly that. With a raw-hex master secret, a tool-initialised
device could not be administered from the Manager and a
Manager-initialised device's words could not be used by hem-tool — the
two reference clients would diverge at the recovery moment. Putting the
derivation in the SDK (not the tool) keeps the quirk in one tested
place and gives every consumer the same bytes. `--master-secret-hex` in
hem-tool stays as a scripted escape hatch (REQ-TOOL-021).

**Acceptance criteria:**
- [ ] Unit: for a fixed 24-word mnemonic the derived 32 bytes equal the
      value produced by the Manager's own code — fixture generated by
      running `jsbip39_v1.js` + `wordlist_english_v1.js` (`toSeed`, then
      `substr(1, 64)`) in a JS engine with that mnemonic, recorded in
      the test with the command used; a second vector proves the
      nibble shift (not `substr(0, 64)`).
- [ ] Unit: generation yields 24 valid words with a correct checksum
      that `ehem_master_secret_from_mnemonic` accepts; a tampered word
      or wrong word count → `EHEM_ERR_ARG`, no derivation; mixed case
      and surrounding whitespace are normalised the way the Manager's
      `.trim()` + NFKD do (and nothing more).
- [ ] Secrets zeroized; ASan/LSan clean; the two symbols exported
      (REQ-API-006 baseline grows by two — additions are legal in 1.x,
      REQ-API-008) and documented in `docs/API-GUIDE.md` (docs_coverage
      gate).
- [ ] Wordlist license confirmed and recorded with the vendored file.
